# CertificateOwl

Proof of concept (March 2023, archived): issue PDF certificates in bulk from a CSV of recipients. Each certificate gets a public link, a QR code that points to it, and a "verify certificate" page where anyone can check a certificate number.

Rails 7.0, Ruby 3.2, Tailwind, `wicked_pdf` for PDFs, `rqrcode` for QR codes.

## How it works

1. **Certificate templates** (`CertificateTemplate`) hold a design plus default text: recipient name, description, issue date, issuer. Two designs ship in `app/views/certificate_templates/templates/`; `db/seeds.rb` creates the matching records.
2. **Groups** (`Group`) are one batch of certificates that share a template, for example one course cohort.
3. **CSV import** into a group creates one certificate per row. The file is semicolon-separated with headers:

   ```
   name;email;modifications.name;modifications.description;modifications.issued_at;modifications.issued_by
   ```

4. Each **certificate** gets a random hex slug, a QR code linking to `https://certificateowl.com/certificates/<slug>`, and a PDF at `/certificates/<slug>.pdf`.
5. **`/certificates/verify`** looks up a certificate number and says whether it exists.

Known gaps: `Certificate#send_email` builds the email but never calls `deliver_later`, so no email is sent; there are no accounts; expiry is a TODO.

## Product notes

Collected from the first version of the idea, vericerti (Legal Hackathon 2022, 3rd place, deleted), and the planning notes written around it. The code here supersedes vericerti; these ideas were never built.

### The pitch

- **Problem:** companies want to give people certificates for what they accomplished, but don't want to enter the data by hand, print or email each one, or host a verification page on their own servers.
- **Solution, in one sentence:** an API (and app) for bulk digital certificates: generation, hosting, verification and emailing.
- **Customers and go-to-market:** direct sales to training and certification companies. Events (hackathons, conferences) are a good first wedge: one batch, many recipients, a clear deadline.
- **The flow, in four steps:** pick a template → add your organization's name, logo and website → upload a recipient list → each recipient automatically gets a unique PDF certificate by email.

### Business model

Variants that were considered:

- **Credits:** a company buys credits for N certificates.
- **Pay as you go vs subscription:** €1 per certificate (free templates, digital seal, never expires), or €50/month for unlimited certificates, premium templates and teams. Certificates issued during a subscription stay valid after it ends.
- **Freemium by volume:** free up to 50 certificates/month, premium up to 1,000/month, all features in both. Free certificates carry a "generated by …" disclaimer.
- **One-off fee per event batch, sized to cover hosting for a fixed period** (for example 2–3 years of domain, hosting and design). It doubles as a promise: the certificates stay online for that period even if the service shuts down. Issuers care about that, because a dead verification link makes the certificate worthless.

### Product ideas

- **Digital seal / stamp:** "connect your own digital seal, or use ours." The most distinctive idea: a verifiable signature makes a certificate harder to fake than a QR link alone.
- **LinkedIn "Add to profile":** put every field LinkedIn's *Licenses & certifications* section needs on the certificate, and offer the one-click [Add to profile](https://addtoprofile.linkedin.com/) link. This is the main reason recipients care.
- **Issuer branding:** organization name, logo and website on each batch, rendered on the certificate. This repo dropped it.
- **A downloadable starter spreadsheet per template** with the right column headers (vericerti generated `.xlsx` files), so people upload a file in the right shape the first time.
- **Short public URLs:** one for the certificate (`/certi/<id>`), one for verification (`/veri/<id>`).
- **Show the PDF inside an HTML page** (an iframe or an Active Storage preview) rather than only as a download.
- **Translated certificates (i18n).**
- **Accounts:** vericerti had sign-up and sign-in, and certificates belonged to the user who issued them.

### Certificate types and layout

- Types: certificate of completion, certificate of appreciation, employee of the week/month, event participation badges.
- Layout anatomy: title ("Certificate of completion", "This certifies that"), recipient name, a subtitle under the name ("has successfully completed the requirements of …"), date, logo, signature (signer's name).

### Data for an event batch

- **Issuer:** company logo, name, website; certificate issued by (person and role, optional).
- **Event:** name, date, website (optional).
- **Each participant:** name, email, role (participant, mentor, judge, winner), achievement (participated, mentored, judged, won), optional extra text.

### API sketch

```ruby
client = Certificates.new(auth_token, secret_token)
client.generate(
  template: "certificate_of_completion",
  title: "Certificate of achievement",
  issued_to: "Jane Doe",
  issued_to_email: "jane@example.com", # emails the certificate when present
  issued_reason: "for completing …",
  issuer_signature: "…",
  issuer_logo_url: "https://…",
  issued_at: nil,                      # defaults to now
  expires_at: nil,
  verification: :qr                    # :qr or :link
)
```

### Build order (as planned)

1. Generate a PDF.
2. Fill it from form data.
3. Several PDF templates with different fields (the hard part).
4. QR code linking to the certificate URL.
5. Email it.
6. CSV import.

### Watch out for

- **Injection:** every recipient field is rendered into HTML and then a PDF, so escape it. A CSV is untrusted input.
